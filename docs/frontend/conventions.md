# Frontend engineering conventions

Read [architecture](architecture.md), the [source map](../../frontend/README.md) and [UI guidelines](../ui-guidelines.md) before changing a product flow. These complement the repository AGENTS instructions.

1. Search existing UI, hooks, styles and API helpers before introducing a new implementation. Keep feature-only components in the feature; share only when real callers need the same contract.
2. Use the actual `app/features/entities/core/api/shared` ownership boundaries. New features need explicit architecture registration; explain deliberate integration paths. Do not add catch-all barrels or source-tree escapes. Source cycles, including type-only cycles, fail checks.
3. Reuse existing primitives, compositions, shell and splitter. Do not add a second component library/layout framework. Preserve native controller IDs, data attributes, adapter names, storage keys, shortcuts and public asset paths.
4. Use semantic palette/typography tokens and existing scoped aliases. Keep feature CSS local, generic styles independent of features. Preserve intentional `!important` bridges to Tailwind and dynamic measured geometry. Check both appearance modes and narrow layouts.
5. Keep temporary interaction state local, filters/selection with the feature, and navigation/focus/geometry with the shell. A new global store needs a concrete cross-feature requirement. Derived values are computed rather than synchronized with effects.
6. Backend snapshots remain remote data; do not reimplement execution lifecycle, access enforcement, Git/workspace rules or persistence semantics in the frontend. Existing conversations are scoped by environment/resource, with pane-owned reading and drafts.
7. Reuse `createAPIClient` and existing request coordinators. Explicit resource/environment identities, stale-result checks and request cancellation protect view changes. Keep errors owned by their operation; unrelated successes must not clear them.
8. Every subscription, observer, timer, socket and object URL has an owner and disposal path. Cleanup must also prevent late callbacks from mutating a new/disposed owner. Let already queued durable saves finish; do not rearm timers after disposal.
9. Keep strict TypeScript. Prefer backend-generated transport contracts, feature presentation props and small explicit types. Validate untrusted persisted/event payloads. Narrow nullable values; do not replace assertions with unchecked casts or blanket Lint suppression.
10. Lint all frontend TS/TSX with existing Biome recommended rules. Narrow, explained suppressions are reserved for verified analyzer false positives (compositional ARIA, interactive splitters, immutable source indices, explicit retry/restore effect triggers). Do not disable rules globally or weaken tests. Existing formatting scopes are retained to avoid mass churn. CSS is built by Vite/Tailwind; Biome's parser does not support all existing Tailwind syntax.
11. Before deleting code, verify static imports, lazy build entries, HTML/Go-host references, CSS, registry composition, platform capability paths and tests. Keep real compatibility boundaries; remove replaced local implementations in the same change.
12. Run affected behavior tests, `npm run check` and `npm run build` for shared changes. Use `npm run app:test`, `npm run chat:test`, `node --test scripts/*.test.cjs`, component/browser suites as applicable. Build assets before backend/native packaging. Compare browser and desktop chrome at the same viewport; distinguish host simulation from actual Tauri verification.
13. AI changes follow the same boundaries: implement the smallest evidence-based change, validate regressions, update owning guidance and remove obsolete code. Do not refactor unrelated areas during a narrow task. Long tasks record baselines, decisions, tests, remaining work and commits in progress; do not claim unexecuted checks passed.

The architecture checker and full TS/TSX lint run under `web:check`, already used by CI. The separate component catalog stays outside production imports. No new permanent audit framework is required; Knip and jscpd can run temporarily with explicit build/controller entries and review of false positives.
